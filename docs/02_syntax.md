# Language Syntax

This document specifies the **syntax layer** of the FreshlyGround language: a formal grammatical model describing 
how valid programs are structured.

The syntax layer specifies:
- the context-free grammar governing a program's form
- the lexical structure of the grammars' atomic units, tokens
- the structural categories that can be composed from those units

## Grammatical Model (EBNF)
FreshlyGround uses **Extended Backus–Naur Form (EBNF)** to define its **context-free grammar (CFG)** over a set of 
terminal symbols (tokens). The grammar describes how a set of tokens may be combined into a well-formed syntactic construction.
As such, it serves as the formal specification for how the parser is to create an AST.

::: tip Formal Definition

The grammar is defined as a 4-tuple:

**G = (Σ, N, P, S)**

Where:

* **Σ** — Terminal symbols (tokens)
* **N** — Non-terminal symbols (syntactic categories)
* **P** — Production rules (rule that defines a non-terminal)
* **S** — Start symbol (`source`; the starting point for all programs)

:::

The first component of the tuple — the terminal symbols (Σ) — is generated by the lexer as a token stream. The parser 
consumes this stream and applies the grammar’s production rules (P) to derive non-terminal symbols (N), incrementally 
constructing a tree structure rooted at the start symbol (S). In this process, terminal symbols form the leaves of the tree, 
while non-terminal symbols represent intermediate syntactic structures defined by the grammar.

## Lexical Model (Tokens)
The lexical layer partitions raw source text into a sequence of **terminal symbols (Σ)** (a.k.a., tokens). 
The construction of those tokens follows the below regular expressions, forming the terminal alphabet of 
the language's grammar.

### Token Classes

```regexp
identifier := [A-Za-z_] [A-Za-z0-9_]* ( - [A-Za-z0-9_]+ )*

operator   := [<>!=] = | [<>+\-*/.,:();=]

integer    := 0 | [1-9] [0-9]*
decimal    := 0 \. [0-9]+ | [1-9] [0-9]* \. [0-9]+

character  := ' ( [^'\n\r\\] | escape ) '
string     := " ( [^"\n\r\\] | escape )* "

escape     := \\ [bnrt'"\\]
```

::: info Note(s)

* Keywords (`LET`, `DEF`, `IF`, etc.) are lexed as identifiers and promoted to keyword tokens during parsing
* Whitespace and comments are not removed by the Lexer
* Spaces in the productions are for readability only; they do not represent literal space characters

:::

## Program Structure

### Start Symbol

At the top of the programmatic structure is the **start symbol (S)**. This can be thought of as the root of the
tree — as it is for the AST — or the top construct that represents the entire program.

```ebnf
source ::= { field } { method }
```
::: tip **Legend:**
- `{ … }` = zero or more
- `[ … ]` = optional (zero or one)
- `|` = alternative
- `Non-terminal symbol ::= Production rule`
:::

### Non-Terminal Definitions

The **non-terminal symbols (N)** of FreshlyGround are constructs that are defined by their relevant
**production rule (P)**, and can be broken down into three main categories:
* **Top level forms** — define program structure and global declarations
* **Statements** — define control flow and state transitions; they do not evaluate to values
* **Expressions** — define value-producing constructs

#### Top-Level Forms

```ebnf
field  ::= "LET" [ "CONST" ] identifier ":" identifier
           [ "=" expression ] ";"

method ::= 
      "DEF" identifier 
      "(" [ identifier ":" identifier { "," identifier ":" identifier } ] ")" [ ":" identifier ]
      "DO"
        { statement }
      "END"
```

#### Statements

```ebnf
statement ::=
      "LET" identifier [ ":" identifier ] [ "=" expression ] ";"
    | "IF" expression "DO" { statement } [ "ELSE" { statement } ] "END"
    | "FOR" "("[ identifier "=" expression ] ";" expression ";" [ identifier "=" expression ] ")"
                { statement }
              "END"
    | "WHILE" expression "DO" { statement } "END"
    | "RETURN" expression ";"
    | expression [ "=" expression ] ";"
```

#### Expressions

```ebnf
expression ::= logical_expression

logical_expression ::=
    comparison_expression
    { ( "AND" | "OR" ) comparison_expression }

comparison_expression ::=
    additive_expression
    { ( "<" | "<=" | ">" | ">=" | "==" | "!=" )
      additive_expression }

additive_expression ::=
    multiplicative_expression
    { ( "+" | "-" ) multiplicative_expression }

multiplicative_expression ::=
    secondary_expression
    { ( "*" | "/" ) secondary_expression }

secondary_expression ::=
    primary_expression
    { "." identifier [ "(" [ expression { "," expression } ] ")" ] }

primary_expression ::=
      "NIL"
    | "TRUE"
    | "FALSE"
    | integer
    | decimal
    | character
    | string
    | "(" expression ")"
    | identifier [ "(" [ expression { "," expression } ] ")" ]
```

::: info Note 
Expressions are defined using a precedence hierarchy.
:::

##### Secondary Expressions (Dot Operator Syntax)

Secondary expressions extend primary expressions to support chained member access using the dot (`.`) operator. Because
secondary expressions are recursively defined over primary expressions, they enable successive member resolution.

Semantically, the dot operator shifts the resolution context so that the `identifier` is resolved within the type 
denoted by the preceding `expression`, rather than within the current lexical (global or method) scope. A detailed 
explanation of this resolution process appears in [Semantics](./04_semantics.md).

::: tip Forms
`expression . identifier`

`expression . identifier ( argument_list )`
:::
